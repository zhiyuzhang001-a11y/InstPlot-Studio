# InstPlot Studio 应用内原位自动更新方案

> 日期：2026-10-01
> 状态：用户已批准实施；macOS 助手真实 GUI 升级/回滚及 Windows 安装器恢复原型已通过，完整平台更新助手与交互验收继续实施。未授权发布或修改 Lite。
> 基线：Studio `0.1.2-rc.2`，已有 GitHub → OSS 签名发布及应用内校验下载。
> 配套：`INSTPLOT_STUDIO_GITHUB_OSS_RELEASE_PLAN.md`、`INSTPLOT_STUDIO_RELEASE_OPERATIONS.md`。
> 审查修订：补齐原位目标、编辑草稿、健康确认及 Windows 恢复原型门；设计审查通过不等于平台升级已验证。

## 1. 目标与范围

用户体验：后台发现新版 → 用户确认下载 → 校验完成 → 点击“重启并更新” → 关闭旧进程 → 原位置升级 → 启动新版。

- 不要求用户找安装包、再次走安装向导；首次安装仍使用正常安装包。
- 保留安装路径、快捷方式、设置、项目和用户数据；不创建第二份应用。
- 下载和提示不打断绘图，允许稍后更新、取消下载及手动检查。
- 更新前处理未保存工作：保存、明确放弃或取消更新；不得强制杀进程或静默丢弃工作。
- 默认仅后台检查，不自动下载、不未经确认退出；以后可单独讨论自动下载偏好。
- 先落地 macOS arm64、Windows x64；Linux 明确区分系统安装和便携安装，不冒充全平台静默更新。
- 不做差分更新、自动跨通道升级、商店分发、遥测或重建发布平台。

“不重复安装”指用户不再重复操作安装流程，不代表禁止内部使用安装器。Windows 可后台调用既有安装器完成原位升级。

## 2. 现状核查与 Lite 参考

核查位置：

- Studio：`apps/instplot-studio/src/app_update.rs`、`src/update.rs`、`packaging/windows/InstPlotStudio.iss`。
- Lite：InstPlot Lite 仓库中的 `src/updater.rs` 和 `packaging/windows/InstPlotLite.iss`；仅作为调查参考，不共用产品配置。

Studio 已有签名清单验证、平台包选择、版本比较、更新序列防倒退、受限下载地址/重定向、大小与 SHA-256 检查、临时文件及取消下载。下载完成后仍要求用户手动安装；并没有原位应用替换或重启事务。

Lite 的 `WindowsUpdater` 在非 debug 构建启动时后台检查，校验后调用 Inno 安装器，参数包含 `/VERYSILENT`、`/SUPPRESSMSGBOXES`、`/NORESTART`、`/CLOSEAPPLICATIONS`、`/NORESTARTAPPLICATIONS`、`/SP-`。安装定义使用固定 AppId、用户目录和最低权限；静默安装后启动新版。

但 Lite 安装器配置 `CloseApplications=force`，启动安装器代码只检查 spawn 是否成功；所查更新模块没有完整的安装完成确认、独立备份回滚及未保存工作保护。不能把这些行为当作 Studio 已达标能力。

借鉴后台检查、进度展示、校验后静默原位升级；保留 Studio 自己的产品 ID、公钥、通道、版本规则和安装身份。不得使用 Lite 的密钥、AppId、OSS 路径或直接共用状态文件。第一步不抽象跨产品框架，避免扩大范围。

## 3. 更新流程与代码边界

状态：Idle → Checking → Available → Downloading → Verified → AwaitingRestart → Applying → AwaitingHealth → Completed；每一步有明确失败、取消和恢复路径。

- `app_update.rs` 负责 UI 和异步任务协调，不承载平台替换脚本全文。
- 现有 `update.rs`/签名模块继续负责信任规则，不降低安全校验。
- 新平台更新模块/助手负责安装位置判定、进程等待、替换、启动与恢复；准确命名在实施前确定。
- 更新助手随产品构建和发布，不运行从清单获取的任意命令或未验证脚本。
- 使用私有更新缓存，不要求选择保存目录。网络请求有超时、限额和取消；UI 不阻塞。
- 下载完成与退出前重新核对包、目标身份、权限、磁盘容量和更新锁；多实例只允许一个更新事务。
- 等待已识别的旧应用进程正常退出，超时取消，不按模糊进程名杀进程。
- 记录持久事务状态：来源/目标版本、受控路径、事务 ID、阶段、备份和错误；断电后可判定恢复，不能只依靠内存状态。
- 新版启动完成核心初始化后回报健康状态；只有确认成功才清理备份。进程启动成功本身不是升级成功。
- 用户配置升级需向后兼容或单独备份可回滚配置；应用恢复不能以破坏配置为代价。用户原始文件不移动、不删除。

### 3.1 工作保护与退出契约

- 复用 `app_controller/coordination.rs` 的 `request_replacement` / `unsaved_dialog` 和 `lifecycle.rs` 的 `save_project`，新增明确的“重启并更新”待执行动作；保存成功且无剩余待处理工作才可退出。
- 不只检查 `EditHistory::is_dirty(document)`：录入数据窗口、文字编辑、轴数值等未提交草稿需要盘点。未提交内容须先应用并保存、明确放弃或取消更新；项目保存成功不能代替草稿保护。
- 保存对话框取消、覆盖冲突未解决、写盘失败、草稿校验失败都取消此次重启，不启动安装器。下载的已验证包可保留以便稍后重试。
- 多实例首版不做跨进程强制退出协议：若同一安装目标另有活跃实例，要求用户自行正常关闭；所有实例关闭、更新互斥锁获取成功后才开始替换。锁需跨进程，不能只用窗口内布尔变量。

### 3.2 健康确认与配置恢复

- 助手通过私有事务目录/受限 IPC 传递事务 ID 和一次性令牌；回执核对目标产品、版本、真实运行路径和进程身份，不接受遗留或其他实例回执。
- 健康确认必须包含配置读取、文档初始化和首个主窗口就绪，不只依赖 `--product-info` 或进程已启动。回执包含架构、进程创建时间并原子持久写入。自动化还需单独验证基础绘图/导出。
- 首版健康握手前暂不开放编辑、自动写配置或不可逆迁移；不新增项目 schema 升级。健康成功后才进入正常工作。恢复设置前核对备份和现值，不静默覆盖候选启动后产生的用户修改。
- 初始超时建议 60 秒（测试可缩短），仅初始化进度可给予有限延长；无回执不是“成功”。候选进程仍在运行时不得直接覆盖它：请求正常退出，无法退出则记录恢复待处理并提示用户，不强杀。
- 配置迁移及健康确认前不写回不可逆新格式；确需写入时先备份明确的用户设置文件。恢复白名单不得包含更新序列防倒退、信任状态、事务锁或日志，不降低安全水位。
- 成功后只清理已验证归属的暂存/备份；失败恢复核对旧版本、身份和可启动性。恢复再次失败时停留明确的可诊断状态并保留可信恢复资产，不无限重试。

## 4. 各平台方式

### macOS

- 以当前正在运行的真实 `.app` 为目标，不硬编码只更新 `/Applications`；核对 bundle ID、版本、架构和安装位置。
- 首版优先复用已签名清单里的 DMG：只读挂载，验证候选 bundle 的结构、身份、版本和签名完整性，复制到目标目录附近的私有暂存位置，卸载 DMG。
- 外置助手等待退出后备份旧 bundle，再将已准备好的新 bundle 放回原路径；所有交换步骤记录状态，失败恢复旧版。不要声称多次 rename 是一项跨文件原子事务。
- 从 DMG、临时目录、只读/受限位置运行时，不自动覆盖未知目标；提示先安装到持久可写位置。系统目录需要授权时明确提示，不绕过权限。
- 保留现有启动/Spotlight 身份，验证唯一应用、版本和实际启动。
- 现阶段没有 Developer ID/notarization；ad-hoc 完整性检查不等于系统信任。不删除 quarantine 或关闭系统安全功能。需实际验证系统是否允许候选启动；不能保证完全无系统提示。
- 首版只自动替换当前用户拥有且可写的持久 bundle；系统目录无需提权且满足校验时可接受，需要授权则提示手动升级，不引入提权助手。防止 App Translocation 将临时运行路径误判为安装位置。

### Windows

- 优先复用固定 AppId 的 Inno 安装器做静默原位升级，而不是自行替换 exe、忽略注册表和卸载信息。
- 按运行位置和可信安装记录确定旧安装位置、用户/机器作用域，显式核对最终目标；不能误用默认目录生成第二份应用。
- 控制器先完成工作保护并正常退出，再由助手等待文件解锁、调用校验过的安装器、等待退出码、核对安装版本和启动新版。
- 只由一个组件负责启动新版，避免安装器与助手双启动。禁止沿用 Lite 的强制关闭作为正常更新策略。
- 固定 AppId、快捷方式、卸载项和配置目录；用真实自定义安装路径进行验收。
- 回滚不只还原 exe：实施前证明安装器恢复策略能覆盖发布文件及安装状态；未证明前不能宣称可自动回滚。
- 管理员安装可能需要 UAC；普通用户安装尽量不提权。未签名包可能有 SmartScreen 提示，不能承诺无提示。

首版明确限定为**已有 Studio 安装记录、当前用户级、可写目录的安装**（现有 `PrivilegesRequired=lowest`）。用户级可信安装记录与实际 exe 路径必须一致；未知安装、便携 exe、机器级安装、权限或作用域不一致时只提示支持方式，不猜路径或引入自动提权。

### Windows 恢复原型：实施前的阻塞门

采用候选路线“已校验的旧安装器恢复原安装”，而不是先承诺任意安装状态都能回滚：

1. 更新前准备当前已安装版本的可信旧安装器及其原签名清单/哈希证据、受控配置备份和安装状态记录；身份、平台、AppId、安装目录一致，恢复所需资产必须已在本机。不能在新程序失败后才联网找旧包。
2. 记录旧版发布文件、卸载项及快捷方式/任务选择；新版安装使用原目录、原作用域和原快捷方式选择，不重新启用用户已关闭的桌面图标选项。图标指向原目录 exe 的产品资源。
3. 助手统一负责正常退出、等待安装器结束与启动，安装器更新模式不独立启动应用。失败时先确认候选与安装器都已退出，再运行旧安装器恢复，核对文件、卸载身份、版本和旧应用启动。
4. 实测旧 Inno 安装器降级恢复、安装中断、卸载状态及新增文件清理。仅恢复旧 exe 不足；只能清理事务记录中由新版本新增、且仍匹配预期哈希的发布文件，不能删除用户文件或不明内容。
5. 当前/旧清单过期不能绕过更新验签规则。旧恢复资产的预先可信留存与离线使用策略必须作为独立恢复契约验证；不得把旧 manifest 当正常远端更新来降低序列水位。未形成可证明的可信来源时阻止自动应用更新。

以上在 Windows CI/VM 故障注入原型通过前，不实现生产替换入口。如果当前版本没有可信旧恢复资产、安装状态无法完整恢复、或降级重装验证失败，旧应用继续运行、保留下载包并说明原因；暂停这一阶段讨论替代方案，不扩建通用安装框架。

首个具备自动更新能力的版本及其后续候选都要实现健康回执；现有 rc.2 手动迁入新版本是引导安装，不要求 rc.2 支持此前不存在的回执协议。跨版本升级还必须验证助手/事务格式向后兼容。

### Linux

- DEB 等系统安装必须通过对应包管理机制和授权；禁止直接覆盖其管理的二进制，不能假装已实现静默自动更新。
- 后续便携包原位替换只能在身份、持久目录、可写性和启动入口明确时支持；保留旧目录直至健康确认。本轮不实施该替换。
- 第一轮明确展示是否支持“一键更新”；不支持时说明安全更新方式，不把“打开下载页”标为自动更新成功。

## 5. 安全与发布衔接

- 复用现有 GitHub/OSS 公网发布，不建新服务，不改既有不可变资产、不覆盖已发布版本。
- 每次实施代码变化使用新版本重新构建发布；不能往 rc.2 包内补写助手。
- 更新只能安装通过产品/平台/架构/通道/版本/序列/有效期检查的签名清单所声明资产。清单签名与平台商业签名是不同保障。
- 更新事务使用受控绝对路径；拒绝路径穿越、链接逃逸和解包越界；包校验后仍防止被替换（私有缓存和使用前复验）。
- 自动启动正式版仅检查 stable，预览版检查 prerelease；不自动切通道。故障回滚至已备份旧版，不降低远端防倒退序列。
- 后台联网节流（建议每次启动最多检查一次且间隔不少于 24 小时），手动检查可立即触发；离线自动检查安静失败。
- 旧版只能下载安装包，因此首次进入具备原位更新能力的新版可能仍需一次手动升级；不得承诺旧客户端凭空获得新能力。
- GitHub → OSS 自动 dispatch 修复 PR #8 独立完成；本文不通过重复发布旧包来验证它。

## 6. 分阶段实施与阶段门

1. **冻结契约**：确认 UI、数据保护、支持安装方式、事务及健康确认协议；确认版本化设置兼容性。输出测试矩阵，不改产品行为。
2. **共用流程**：后台检查、私有缓存、状态机、取消、互斥和持久事务；全部用本地签名测试源验证，不触碰生产 latest。
3. **macOS 原位升级**：先完成本机主要安装位置的升级/失败恢复/未保存工作测试；成功后再进入下一平台。
4. **Windows 原位升级**：结合 Lite 经验完成真实安装器升级、恢复和自定义路径测试；Windows 实机或 VM 验证，不以 macOS 单测替代。
5. **Linux 分流与回归**：第一轮仅做安装方式识别和清晰安全提示；DEB/便携自动替换都不作为本次上线承诺。验证既有数据、绘图、导出和更新安全测试；Linux真正一键更新另立后续阶段。
6. **预览发布与端到端验收**：用户批准后创建新版本，先验证 rc.2 手动迁入首个支持助手的版本，再验证“首个助手版 → 下一助手版”的真实自动升级及回滚；每个平台记录版本、路径、退出/重启、设置、资产校验和恢复证据，最后才更新经用户批准的预览通道，不启用 stable。

每阶段只做对应模块改动，保留无关工作；定向测试先行，共用安全模块改动再跑相关全量测试。GitHub 长耗时任务低频查看结果，不持续监听。发布和全局配置修改不能由写方案自动授权。

阶段门证据分层：共用阶段提交离线单测/故障模拟；macOS提交真实 bundle 升级与恢复记录；Windows先提交原型的正常升级、降级恢复、自定义路径、取消/失败和快捷方式证据，再开放产品入口。CI资源检查或安装器退出码不能替代桌面实机/VM确认。没有相应环境就标记待验证，不标记完成。图标修复是独立前置工作，其尚未发布的本地改动不算已装客户端能力。
