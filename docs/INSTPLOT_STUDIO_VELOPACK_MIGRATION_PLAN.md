> 归档状态（2026-10-10）：能力门未通过，未迁移 Velopack。后续采用现有更新机制完成修复、真实 GUI 验收与公开 rc.3 技术 prerelease；本文的“当前”“下一步”和授权描述均为 2026-10-09 的评估阶段历史，不自动恢复迁移任务。见[发布收尾记录](INSTPLOT_STUDIO_RC3_RELEASE_CLOSEOUT.md)。

日期：2026-10-09。状态：已独立审查修订，并开始执行阶段 1；官方固定版本能力审计发现硬阻断，尚未接入、安装或发布 Velopack。详见 `INSTPLOT_STUDIO_VELOPACK_FEASIBILITY.md`。

## 目标与当前授权

用成熟框架承担安装及更新执行，减少自制助手的维护负担。目标交互为：启动后台检查 → 有更新时提示 → 用户点击更新 → 后台下载并显示进度 → 保护未保存工作 → 正常退出、更新、单次重启。

用户已授权独立 agent 审查、修订计划并执行到完成。授权覆盖符合现有保护的适配检查和独立原型；不自动授权改变安全契约、修改生产更新源、删除旧实现、替换现有安装或读取生产私钥。执行须遵循下面的决策门；出现硬阻断时报告真实结果与所需决策，不能用“直到结束”推定允许降低保护。

范围先限定 Windows x64；不重写 Rust/eframe 绘图界面，不改变项目格式，不同时迁移 macOS/Linux 更新器。没有更新或网络不可用时，正常使用软件；用户可以推迟更新。

## 已知事实与待核实事项

- Velopack 官方提供 Rust SDK，包括检查、下载及应用更新后重启接口。
- 支持 HTTP 静态分发；可以评估继续用 OSS 托管其索引和更新包，不假定现有签名清单格式可直接复用。
- 更新要求使用 Velopack 打包并安装。现有 Inno Setup 安装需要迁移设计，不能仅替换 SDK 后直接升级。
- 框架采用 MIT 许可，可自托管；无需采购其托管服务。仍有 OSS/CI 成本，代码签名证书另行评估。
- `vpk` 打包工具需要 .NET SDK；这是构建端要求，不据此要求所有 Rust 客户端安装 .NET。
- 自定义 D 盘目录、安装身份、快捷方式、签名信任、防回退、应用健康失败恢复及缓存保留策略均待验证。不能将框架的“更新成功”直接等同于 Studio 项目已恢复且 GUI 正常。

2026-10-09 固定官方 `1.2.161` / commit `92d6a1c91716729d449034df5c50307dcce39493` 的源码审计已确认：Windows apply 无条件调用安装根进程强制终止；退出等待错误后继续执行；旧目录备份在新版 GUI 健康检查前清理。静态 HTTP SDK 校验大小和摘要，不等价现有发布者签名及持久序列水位。前两类执行/恢复行为不能仅靠 GUI 薄适配保证现有契约，目前不准进入安装原型。没有执行 Windows 测试，不能声称这些故障已实测。

现有 Windows rc.2 可供正常使用，但本聊天实机 rc.2 → rc.3 重启更新未成功完成；观察到 GUI 卡顿和取消路径锁冲突。之后仍为 rc.2，尚无足够证据判断是否发生安装后回滚。不把 CI 安装恢复原型视为真实 GUI 更新验收。

## 阶段 1：适配与安全检查

产出：固定框架/SDK/打包工具版本及许可记录，一份旧契约到新框架的责任映射。

必须在下载构建工具、依赖接入和两版本打包前完成此门。固定 SDK 与 `vpk` 同版本；不得用变化的 `latest` 文档代替固定源码。实际执行阶段须记录 runner/工具环境；源码审计不冒充平台运行。

核实以下边界：

1. Rust 1.98、当前启动入口及 GUI 事件循环的兼容性；阻塞操作必须在工作线程执行。
2. 用户级安装、目录可选性、快捷方式和唯一卸载身份；不能承诺沿用 D 盘原目录，须以真实安装结果决定。
3. HTTPS、可信发布身份、包真实性及完整性、更新源限制、防回退和密钥轮换。包哈希不能代替发布者签名认证。
4. 独立更新进程的正常退出等待、多实例、超时、取消、安装中断及重启语义。
5. 框架实际提供的失败恢复范围：安装失败与新程序启动后健康失败必须分开记录。
6. 项目、配置与安装文件的隔离，用户数据不进入安装器清理范围。

若关键能力缺失，先明确差距和最小补充设计。若仍需重新自建大套事务/恢复引擎，或只能降低现有保护，则停止评估并报告，不继续扩大投入。

当前门结果：不通过。独立审查与主 agent 均复核固定源码；尚未找到官方可关闭强制终止并保留健康恢复备份的受支持配置。不得默默 fork 框架、把健康失败恢复改为手动重装，或把“先退出主实例”当成其他实例不会被强杀的证明。

## 阶段 2：独立双版本原型（第一决策门）

使用独立应用 ID、测试快捷方式、私有安装/数据目录和测试更新源。不得与现有 Studio 的注册表、配置、缓存或恢复记录共用身份。

前置条件：阶段 1 通过，或用户针对已列出的契约差异明确批准新方案并修订契约。当前不满足；此阶段尚未开始。测试包只能交付专用测试账户/一次性环境；代码签名、清单签名、包摘要是不同证据，分别记录，不能混算。

先使用本地测试源验证，再在获批后使用独立 OSS 路径验证。不得直接使用生产 latest；测试签名和发布身份与生产隔离，不读取生产私钥。

制作两个固定版本 A/B，记录源码 SHA、框架版本、工具版本、构建配置、资产大小及 SHA-256。

必须取得 Windows 实际证据：

- A 安装并正常打开；发现 B 后一次确认完成下载、退出、更新和单次重启；实际版本为 B。
- 安装位置、快捷方式和卸载身份正确；项目与配置哨兵内容不变。
- 下载和准备期间窗口响应正常；连续点击不启动重复事务，多实例不竞争安装。
- 离线/下载失败/错误包不改旧安装；退出前取消不丢工作；安装阶段的取消规则明确。
- 未正常退出、安装中断、候选无法启动或健康失败均有明确结果、日志及安全恢复办法；自动恢复能力未证实则明确标为缺口。
- 实测 A/B 安装包大小、安装后总占用、更新缓存、升级峰值占用和完成后保留内容。不得未经批准删除旧恢复资产来获得好看的体积数字。

通过条件：正常 GUI 升级真实成功，关键安全与恢复边界符合当前有效契约并有证据。补充方案写在纸上不算通过，改变契约必须有用户明确批准。只有编译/CI 通过不算通过。失败则先评估是否值得继续，不直接进入正式迁移。

## 阶段 3：Studio 最小集成

只在原型通过并获批后开始：

- 建立薄更新适配层，由 Velopack 承担更新执行，不同时运行旧助手。
- 启动后后台检查；同一候选版本不反复弹窗，提供“更新”和“稍后”。
- 主流程仅一个更新按钮，阶段与进度清晰；发布说明可作为次要链接，缓存目录不作为常规操作步骤。
- 下载/验证/准备不阻塞 GUI；退出前检查未保存项目及未应用草稿。保存失败或用户取消则不退出、不安装。
- 正常重启时恢复需要重开的项目；真实首画布及项目可用性与仅进程存活分开验证。
- 普通生产构建保持现有关闭状态，直到相关验收及启用审批完成。

## 阶段 4：打包与 OSS 测试分发

- 构建安装器及 Velopack 更新资产，固定版本；不把现有 Inno 包误当作 Velopack 更新包。
- 使用独立测试前缀和发布身份，精确绑定 source/run/attempt/配置/哈希。
- 构建一次，后续部署消费同一核验资产；不可变包不得覆盖。测试 latest 的激活是明确且可审计的单独操作。
- 上传后从公网重新验证索引、真实性、资产大小/哈希和准确版本，不以上传退出码代替公网验收。
- 不修改现有生产 version/trust/latest，不创建产品 tag/Release；正式分发另行批准。

## 阶段 5：旧 Inno 安装迁移与最终验收

先明确一次性迁移是新安装、受控交接还是其他受支持方式，再给用户步骤。不能承诺无感原目录覆盖，也不能要求用户先卸载来掩盖迁移缺口。

验证当前账户、现有 D 盘安装、中文/空格路径、旧配置/项目、快捷方式及卸载项；迁移失败时现有程序和用户数据仍可用。不得擅自删除原安装、旧缓存或恢复备份。

最终清单包括：普通启动、发现更新、一键升级、单次重启、项目恢复、取消、多实例、离线/坏包、权限不足、安装中断、健康失败及恢复。每项标明真实 Windows GUI、原生自动化、单元测试或未执行，不能混算。

全部相关门槛通过并获批后才切换生产引擎；旧实现退役与清理作为独立步骤，不在试验期间删除。

- 初步预算：适配检查及独立正常升级原型约 1–2 个工作日；通过后最小集成/分发/迁移约再 3–5 个工作日。是未实施前的工程估算，不是保证，也不代表这些时间内完整故障矩阵必然通过。

- 体积收益未知，以实际包和安装占用为准；不预先宣称更小或固定开销。
